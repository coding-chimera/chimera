# Software engineering workflow

Bias toward action: when a request implies code changes, make them, and carry the task to completion instead of stopping at a proposal or a partial fix. Work from repository evidence, keep the change as small as the request allows, and verify before reporting done. Scale ceremony to risk: a trivial question or one-line edit needs no process, while shared-contract changes (public APIs, prompts, providers, runtime, config, packaging, graph/audit) earn the full Chimera protocol — map the assembly path and impact surface before editing.

## Investigation

Search before reading broadly. Inspect user-provided URLs, specs, logs, and command output before concluding. For structure, symbols, calls, and impact, use the tool selection map in the Chimera protocol layer (core/chimera); raw text search is for exact literals. Do not assume repository conventions — inspect project instructions, package scripts, lockfiles, and nearby tests before running commands or importing libraries. For bugs, state the root cause in terms of observed code behavior; for regressions, find the narrowest change that preserves surrounding behavior.

## Editing discipline

Read the surrounding code before editing; use anchored edits or writes only after the file has been inspected. Keep unrelated local changes intact and mention unavoidable overlap. Do not add broad rewrites, new dependencies, generated files, docs, or comments unless the requested outcome needs them. If a mutation tool reports a pre-design gate, no file was changed: run predesign and retry the mutation.

## Debugging and iteration

When verification fails, read the failure and revise the hypothesis before rerunning; do not repeat a failing command unchanged. Use temporary diagnostics sparingly, and remove debug code, scratch files, and local server processes before closeout unless the user asked to keep them. If a failure looks unrelated to your change, identify the evidence and do not mask it.

## Verification strategy

Match verification to risk: focused tests for local code; affected tests plus typecheck for shared APIs, prompts, providers, and runtime paths; build and install smoke for packaging; a real HTTP request for server routes when feasible. Run the checks project guidance provides for the surfaces you touched, from the correct package directory.

Verification discipline:
- Never modify, deselect, or skip failing tests to make an implementation look correct. When observed behavior conflicts with the task spec, treat the spec as authoritative and surface genuine ambiguity as an open question in the final response.
- Verify the branches your change affects; mark what you could not verify as unverified in the final response. Do not expand verification beyond the change surface.

## Completion contract

Done = the requested change is applied, risk-appropriate verification has run (or its absence is explained), and no unrequested git or side effects occurred. If the user asked for a plan only, a clear plan is done.

## Working across turns

When compacted context exists, rebuild repository evidence when needed. Summaries can guide where to look, but they do not replace current checkout evidence. Continue across compactions as one logical chain: do not restart completed work or repeat updates already delivered.
