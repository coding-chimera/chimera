Run a model-authored orchestration program that fans out subagents in one call. It is the tool for multi-stage pipelines, heterogeneous parallel work, dynamic control flow, and in-program dedupe/synthesis — not a default wrapper for single one-off work.

`code` is the body of an async JavaScript function (top-level `await` and `return` are allowed). It receives one binding object, `orche`:

- `await orche.agent({ prompt, agent?, model?, label?, schema? })` dispatches one subagent and resolves to `{ text }`, or `{ structured }` when `schema` is given, or `null` when that subagent fails. A `schema` turn that ends without valid structured output gets a corrective user turn in the same child session (same schema, default 2 retries). If retries are exhausted but the child produced text, the call resolves to `{ text }` (a fallback: inline text is capped near 8KB, and when truncated the returned text carries the `outputFile` path for the full text) instead of `null` — `structured` is then undefined. The compaction-window rule only decides whether retrying continues; a round that already produced valid structured output returns directly, unaffected by compaction.
- `await orche.parallel([() => orche.agent(...), ...])` runs the tasks concurrently and returns results in input order; an individual failure becomes `null`.
- `orche.pipeline([stage, ...])([item, ...])` runs every item through the stages in order; a failed stage yields `null` for that item and skips its remaining stages.
- `orche.log(...values)` or `console.log(...)` appends a line to the tool result log.
- `return <json>` ends the program. The return value must be lossless JSON and is the curated result of the call.

Load the orchestrate-authoring skill (script API, failure semantics, limits, quality patterns, worked examples) via the skill tool before the first program of a session and before any multi-stage program. Do not write a non-trivial program from memory.

Context isolation: subagent intermediate messages, tool output, and full transcripts never enter this session's context. Only your `return` value and `orche.log` / `console.log` output come back, so the program must actively select and return exactly what the parent needs — for example a compact array of findings, a deduplicated table, or a verdict, not raw child transcripts.

Use when: the work genuinely needs program shape — a multi-stage pipeline, heterogeneous parallel work with a different prompt/agent per axis, dynamic control flow (loops, conditional fan-out, in-program dedupe or synthesis), or complex continuous collaboration where later stages depend on earlier results. Use `orchestrate` only when you can plan the whole program up front — every stage, every worker prompt fully contextualized, control flow and return shape decided — and then hand it off and wait for the result. Size the program from the task: 2-4 agents for small work, 5-9 for medium, 10-30 for large; `maxTotalAgents` and the concurrency window are backstops, not thresholds.

Do not use when: the work is one single-layer one-off research, implementation, review, or verification axis — use `task`; or it is a homogeneous single-layer bounded fan-out over one prompt shape — use `chimera_swarm` with explicit `items` + `prompt_template`, or a preset/`from` source. `orche.batch` belongs inside a larger program that has staged or synthesis needs; a simple homogeneous batch goes straight to `chimera_swarm`. A single-agent program is justified only when the program's own capabilities are needed (for example JSON-schema correction turns or dynamic control flow); do not wrap an ordinary investigation in a program that only returns its conclusion. If you cannot commit to that complete plan before dispatch (the work needs iterative steering, exploratory back-and-forth, or worker prompts you cannot yet specify), do not use `orchestrate`; use `task` / `chimera_swarm` or direct work instead. A hard blocker (shared files, ordering constraints, provider limits) can justify a narrower shape, including falling back to `task` or a read-only path when the orchestration tooling itself is failing.

Before the first dispatch of a task, write one plan line in your reply: phases, estimated agent count, and what each phase returns. Update it when the phase structure changes. This is a preview, not a permission request; write it and execute immediately. Token cost is not a reason to shrink the plan.

Approval: `orchestrate` is approved once per call, and every `orche.agent` additionally goes through the normal `task` approval for its agent type. Subagents are real child sessions (visible, persisted, cancellable) and obey delegation depth, concurrency, and per-agent permission limits.

Failure semantics: a subagent task failure resolves to `null` and the program continues; host-side problems (invalid arguments, dispatch infrastructure, an approval denial) reject that binding call, and an uncaught rejection terminates the program with an error. Returning completes the program; uncaught exceptions, orchestration-worker failures (including output/protocol errors), a positive `timeoutMs` budget expiring, or user cancellation terminate the run.

`timeoutMs` controls the global wall-clock budget. Use `timeoutMs: 0` for an unlimited run (recommended default); negative values and omission also mean unlimited, with no global timer. `null` is rejected by the schema. A finite positive number enables a deadline; it is rounded down to whole milliseconds with a 1ms floor (so `0.5` is 1ms) and no upper cap. Set a positive budget only when you deliberately want a time limit. `timeoutMs` is an outer tool argument, never an `orche.agent` field.

The outer tool arguments are JSON. Prefer this complete template and change only what the task needs:

```json
{ "description": "Run without deadline", "code": "return { ok: true }", "timeoutMs": 0, "maxTotalAgents": 64 }
```

`timeoutMs: 0` means no global timer; omission and negative values are also unlimited, but the explicit `0` is preferred over deleting the field. `maxTotalAgents` caps total child dispatches (default 64, hard cap 256) — 64 is the built-in default, so keep it unless the task needs a different cap.

`background` (default `false`) registers the program as a program-level background job: with `background: true` the call returns a startup receipt immediately, every worker completion injects an `<orchestrate_worker_result>` notification into this session, and the program's final result arrives as an `<orchestrate_result>` notification. Prefer `background: true` for any program: dispatch it, then continue other work or end the turn; the notifications wake you to synthesize. Never block the session with sleep, polling, or busy-waiting for the program's result.

A foreground call is only for a result strictly required inline to continue this same turn, and must pass `block_reason` naming that concrete dependency.
