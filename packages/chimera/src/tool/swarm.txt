Run a bounded set of subagent tasks from one worker prompt shape.

Use this tool only when the active multi-agent policy permits delegation and you already have at least two genuinely independent, non-overlapping work items that benefit from parallel execution. Common Chimera v1 flow is audit evidence -> preset/template + items -> bounded subagent fan-out:
1. Gather evidence with `chimera_audit_recent`, `chimera_audit`, `chimera_obligations_list`, or `chimera_oracle_recent`.
2. Call this tool with either explicit `items` or a supported `from` source.
3. Prefer a `preset` for common Chimera work; use raw `prompt_template` only when the preset shape does not fit.
4. Summarize child results yourself, resolve any scope/conflict warnings, apply any parent-side follow-up, then rerun audit/tests/oracles as needed.

Presets are worker prompt shapes. They are not workflow engines, permission switches, file locks, automatic repair loops, or proof that work is complete. A child subagent may edit only when its normal tools and the chosen preset/prompt allow it.

This is a thin fan-out helper. It does not build PlanGraph, lock files, claim obligations, apply edits itself, rerun audits, or decide convergence for you. The parent agent owns conflict handling, final audit/test/oracle verification, and closeout. Tool output includes parent closeout recommendations after each run.

The tool publishes each worker incrementally through `metadata.childRuns` (`queued`, `running`, `completed`, `error`, or `cancelled`) and keeps `childSessions` plus final output for compatibility. Child sessions are normal subagent sessions that frontends can display, enter, and stop individually. If the parent swarm is aborted, already-created child sessions are cancelled as part of the same abort flow. Treat any interrupted child report as incomplete evidence that the parent must re-check or rerun deliberately.

Concurrency defaults to 16 and is capped at 16. Treat 16 as a capacity ceiling, not a target: use full concurrency only for independent work with disjoint scopes, and lower it for shared files, ordered dependencies, provider limits, or contended state.

Optional `workload`: declare one homogeneous delegation archetype for the whole fan-out. Pass `workload` alone to let the current cost-aware scheduler select one concrete route and non-ultra variant, which every worker reuses. Pass `workload` with `model_profile`, `model`, or `model_identity` to keep that explicit selector authoritative while validating and recording the workload for attribution. Unknown workload names are rejected with the current valid names. Split heterogeneous work into separate swarms.

Optional `model_profile` names a `delegation.model_profiles` entry and applies its configured model and variant to the fan-out.

Optional exact selection: pass `model` as a current `provider/model` route, plus `variant` only when that route advertises it. Subagents do not support the `ultra` variant; it is reserved for root sessions.

Optional identity selection: pass `model_identity` to resolve a current runtime identity once before starting workers. Add `provider` only to narrow the identity to one current provider. Use `subagent_model_routes` when identity routes are ambiguous; do not invent provider IDs or deployment names.

`model_profile`, `model`, and `model_identity` are mutually exclusive; `workload` is orthogonal to them. The tool resolves and validates the final route, asks `task_model` for that concrete `provider/model` once, and creates no child if resolution or authorization fails. Every worker then reuses the same prepared route.

Swarm workers cannot call `task` or `chimera_swarm`; nested fan-out is disabled so one parent swarm cannot recursively multiply its concurrency.

Prompt templates support:
- `{{item}}`: formatted item text or JSON
- `{{index}}`: 1-based item index
- `{{total}}`: total item count

Explicit object items may include conventional scope hints such as `files`, `file`, `path`, `target`, or `scope.files`. When multiple explicit items mention the same file, the tool emits advisory scope warnings and prefixes affected worker prompts. Warnings do not lock files, deny execution, or prove a conflict; the parent agent must decide whether to lower concurrency, split items, or proceed.

Supported `preset` values:
- `audit-followup`: handle one audit/obligation item. If there is a clear narrow fix, the worker may make scoped edits, run focused verification, and report changed files; otherwise it should classify the item as actionable, covered, irrelevant, duplicate, blocked, or no-issue.
- `audit-review`: read-only review of one audit/obligation item; classify whether it is actionable, irrelevant, duplicate, stale, or out of scope.
- `oracle-followup`: investigate one failing/unknown oracle and explain or fix the likely cause within a narrow scope.
- `file-review`: read-only review of one explicit file/item for risks or follow-up.

Preset worker prompts ask for structured labels: Status, Changed files, Verification, Remaining risk, and Parent follow-up. Treat these labels as child reports for the parent to inspect, not as automatic obligation resolution.

Supported `from` sources:
- `pending_obligations`, `claimed_obligations`, `active_obligations`: default to `audit-followup`.
- `stale_obligations`: defaults to `audit-review`.
- `failing_oracles`, `unknown_oracles`, `failing_or_unknown_oracles`: default to `oracle-followup`.

For parallel editing, keep items independent and scoped by file/range/symbol when possible. Workers must not broaden into unrelated refactors or take over other swarm items; the parent agent must rerun relevant checks, resolve conflicts, inspect structured child reports, and handle obligation claim/resolve/ignore decisions explicitly.

Minimal call examples:
- `{ preset: "audit-followup", from: "pending_obligations", concurrency: 8 }`
- `{ prompt_template: "Item {{index}}/{{total}}: {{item}}", items: ["Review src/auth.ts", { file: "src/api.ts", scope: "route handlers", questions: ["callers?", "error paths?"] }] }`
