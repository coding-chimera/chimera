Run a bounded set of subagent tasks from one worker prompt shape.

Hard boundary: use `chimera_swarm` only when the fan-out consumes a preset or `from` audit-evidence source. Every other multi-agent task runs through one `orchestrate` program.

Use this tool only when the active multi-agent policy permits delegation and you already have at least two genuinely independent, non-overlapping work items that benefit from parallel execution. For foreground programmatic fan-out, use `orchestrate` instead. Common Chimera v1 flow is audit evidence -> preset/template + items -> bounded subagent fan-out:
1. Gather evidence with `chimera_audit_recent`, `chimera_audit`, `chimera_obligations_list`, or `chimera_oracle_recent`.
2. Call this tool with either explicit `items` or a supported `from` source.
3. Prefer a `preset` for common Chimera work; use raw `prompt_template` only when the preset shape does not fit.
4. Summarize child results yourself, resolve any scope/conflict warnings, apply any parent-side follow-up, then rerun audit/tests/oracles as needed.

## Background vs foreground dispatch

Prefer `background: true` for almost every swarm. It returns a startup receipt immediately, lets you keep planning or dispatch more work, and reports each worker back to this session when it finishes. Use a foreground swarm (omit `background`, or pass `background: false`) only when you genuinely cannot proceed without every worker result inline; in that case you must set `block_reason` naming the concrete dependency that forces the wait.

With `background: true`:
- The tool returns a startup receipt before workers settle. The receipt contains `background: true`, `childRuns` (already-started workers `running`, the rest `queued`), `childSessions`, and a `note`; it does not aggregate final results or success/failure counts.
- Every worker completion injects exactly one `<swarm_worker_result>` notification into this session. Each notification starts with `task_id: <worker child session id> (swarm worker completed)`, then carries `index`, `title`, `status`, `summary`, and `output_file`. A start failure (including a full background pool) produces one `(swarm worker error)` notification with `status: error` and an `error` field instead.
- DO NOT sleep, poll, or proactively check on worker progress. Wait for the injected notifications, then synthesize. If you must cancel one worker, call `task_cancel` with that worker's `task_id` (the child session id); do not cancel the whole swarm through the tool.
- Background workers occupy the shared `delegation.background_concurrent` pool (default 16). The swarm's own `concurrency` cap still bounds how many run at once; when the pool is full a worker is rejected with an error notification rather than queued forever. Foreground swarms do not consume that pool.
- After the tool returns, the receipt's `childRuns` metadata is frozen: it is a startup snapshot, not a live status feed. Frontends derive live worker state from the child sessions themselves; do not expect this tool part to be updated later.
- A parent turn abort does not cascade into detached background workers. They are owned by this session through the background-job engine, so `session.remove` and the session cancel cascade still stop them.

With `background` omitted or `false`, the tool waits for all workers, consumes results inline, and returns the aggregated `results`/`success`/`failure`/`parentCloseout` payload. Aborting the parent turn cancels the in-flight workers. Set `block_reason` whenever you take this foreground path.

When `delegation.background_subagents` is `false` (kill-switch), the `background` parameter is not exposed at all and the tool always runs the foreground path.

Presets are worker prompt shapes. They are not workflow engines, permission switches, file locks, automatic repair loops, or proof that work is complete. A child subagent may edit only when its normal tools and the chosen preset/prompt allow it.

This is a thin fan-out helper. It does not build PlanGraph, lock files, claim obligations, apply edits itself, rerun audits, or decide convergence for you. The parent agent owns conflict handling, final audit/test/oracle verification, and closeout. Foreground output includes parent closeout recommendations; background receipts leave that synthesis to the notifications you receive later.

Workers are normal subagent sessions that frontends can display, enter, and stop individually. Treat any interrupted child report as incomplete evidence that the parent must re-check or rerun deliberately.

Concurrency defaults to 16 and is capped at 16 — this caps how many workers run at the same time, not how many items you may submit; excess items queue automatically. It is safe and encouraged to split large tasks into as many clear, independent items as the work supports: for read-only exploration and investigation, more workers mean broader and more detailed coverage. Lower concurrency only for shared files, ordered dependencies, provider limits, or contended state.

Minimal call — no selector fields are needed:

{ prompt_template: "Review {{item}}", items: ["src/auth.ts", "src/api.ts"], background: true }

Omit every optional selector you are not using (`workload`, `model`, `model_profile`, `model_identity`, `provider`, `variant`). Omit the key entirely; never pass `""`, `null`, or `"none"`, because an empty string counts as a supplied value and fails mutual-exclusion validation. Pass `workload` alone to let the scheduler route every worker; pass at most one of `model`, `model_profile`, or `model_identity` to pin a route, and add `workload` only when you also want its attribution/validation.

Optional `workload`: declare one homogeneous delegation archetype for the whole fan-out. Pass `workload` alone to let the current cost-aware scheduler select one concrete route and non-ultra variant, which every worker reuses. Pass `workload` with `model_profile`, `model`, or `model_identity` to keep that explicit selector authoritative while validating and recording the workload for attribution. Unknown workload names are rejected with the current valid names. Split heterogeneous work into separate swarms. A model excluded from the declared workload by `delegation.scheduling.archetypes.<workload>.excludeModels` fails the whole fan-out before any child is created (resume excepted); choose another model or omit workload.

Optional `model_profile` names a `delegation.model_profiles` entry and applies its configured model and variant to the fan-out.

Optional exact selection: pass `model` as a current `provider/model` route, plus `variant` only when that route advertises it. Subagents do not support the `ultra` variant; it is reserved for root sessions. When `variant` is omitted for a model that advertises variants but configures no default options, dispatch fills the highest non-ultra variant so providers that require a reasoning effort keep working.

Optional identity selection: pass `model_identity` to resolve a current runtime identity once before starting workers. Add `provider` only to narrow the identity to one current provider. Use `subagent_model_routes` (if not in your tool list, reveal them with `tool_search`) when identity routes are ambiguous; do not invent provider IDs or deployment names.

`model_profile`, `model`, and `model_identity` are mutually exclusive; `workload` is orthogonal to them. The tool resolves and validates the final route, asks `task_model` for that concrete `provider/model` once, and creates no child if resolution or authorization fails. Every worker then reuses the same prepared route.

Workers may dispatch further subagents only when their agent type declares the `task` permission and the delegation chain is below `delegation.max_depth` (default 3 including the root session). All concurrently running subagents share the runtime-wide `delegation.max_concurrent` budget (default 128): dispatches that exceed the budget queue until capacity frees, and a worker waiting on its own children does not consume budget. Keep worker fan-out shallow — prefer widening the current swarm over nesting another one.

Prompt templates support:
- `{{item}}`: formatted item text or JSON
- `{{index}}`: 1-based item index
- `{{total}}`: total item count

Explicit object items may include conventional scope hints such as `files`, `file`, `path`, `target`, or `scope.files`. When multiple explicit items mention the same file, the tool emits advisory scope warnings and prefixes affected worker prompts. Warnings do not lock files, deny execution, or prove a conflict; the parent agent must decide whether to lower concurrency, split items, or proceed.

Supported `preset` values:
- `audit-followup`: handle one audit/obligation item. If there is a clear narrow fix, the worker may make scoped edits, run focused verification, and report changed files; otherwise it should classify the item as actionable, covered, irrelevant, duplicate, blocked, or no-issue.
- `audit-review`: read-only review of one audit/obligation item; classify whether it is actionable, irrelevant, duplicate, stale, or out of scope.
- `oracle-followup`: investigate one failing/unknown oracle and explain or fix the likely cause within a narrow scope.
- `file-review`: read-only review of one explicit file/item for risks or follow-up.

Preset worker prompts ask for structured labels: Status, Changed files, Verification, Remaining risk, and Parent follow-up. Treat these labels as child reports for the parent to inspect, not as automatic obligation resolution. Background notifications render them into the `summary` field.

Supported `from` sources:
- `pending_obligations`, `claimed_obligations`, `active_obligations`: default to `audit-followup`.
- `stale_obligations`: defaults to `audit-review`.
- `failing_oracles`, `unknown_oracles`, `failing_or_unknown_oracles`: default to `oracle-followup`.

For parallel editing, keep items independent and scoped by file/range/symbol when possible. Workers must not broaden into unrelated refactors or take over other swarm items; the parent agent must rerun relevant checks, resolve conflicts, inspect structured child reports, and handle obligation claim/resolve/ignore decisions explicitly.

Minimal call examples:
- `{ preset: "audit-followup", from: "pending_obligations", concurrency: 8, background: true }`
- `{ prompt_template: "Item {{index}}/{{total}}: {{item}}", items: ["Review src/auth.ts", { file: "src/api.ts", scope: "route handlers", questions: ["callers?", "error paths?"] }], background: true }`
- `{ prompt_template: "Item {{index}}/{{total}}: {{item}}", items: ["blocking check"], block_reason: "closeout needs this result inline" }`
